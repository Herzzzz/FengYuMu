# 枫语幕 4.0 · 验证与调优依据

本文件记录 v4.0 施工期间实测到的性能基线与一项阈值诊断结论。
数据来自本机实测，用于复核与后续实机调优对照，本身不是产品测试。

测量环境：Windows、PowerShell 5.1、`csc.exe`（.NET Framework 4.0）、
显示器 2560×1440、MapleStory 客户端客户区 1920×1200（窗口化、非全屏）。

## 一、性能硬指标

基准方式：`枫语幕.exe --benchmark --benchmark-image=<png>`，
`last_run.txt` 现额外输出「首次可见耗时」与「最终收敛耗时」两行。

| 场景 | 首次可见 | 最终收敛 | 验收目标 | 结论 |
|---|---|---|---|---|
| 任务面板（QQ20261007-173014） | 668 ms | 1227 ms | 首显 ≤800 / 收敛 ≤1600 且不恶化基线 10% | 达标 |
| 公民任务（QQ20261007-144653） | 562 ms | 679 ms | 同上 | 达标 |
| 任务面板（QQ20261007-123533） | 562 ms | 726 ms | 同上 | 达标 |
| 任务+装备（QQ20261007-124246） | 708 ms | 1029 ms | 同上 | 达标 |
| 无面板合成画面 | 323 ms | 872 ms | 首显 ≤350 | 达标 |
| 合成文本（无面板） | 316 ms | 837 ms | 同上 | 达标 |

统一入口：`tools\Measure-TranslationPerformance.ps1`（自动启用自动化闸门，
并保证以 CreateProcess 而非 ShellExecute 启动产品，避免桌面弹窗）。

### 置信度分布与可无缝标签数

`last_run.txt` 新增两行诊断输出：`置信度分布=高:x 中:y 低:z` 与 `可无缝标签=n`，
用于从基准运行直接核对快速首显的准入条件与 Seamless 的前提是否成立。

| 实测图 | 命中 | 置信度分布 | 可无缝标签 |
|---|---|---|---|
| QQ20261007-173014 | 9 | 高:9 中:0 低:0 | 9 |
| QQ20261007-144653 | 2 | 高:2 中:0 低:0 | 2 |
| QQ20261007-124246 | 4 | 高:4 中:0 低:0 | 4 |

合计 15 个标签全部为高置信度、全部带 `SourceBounds`。这证明：

1. **擦除区域已覆盖全部标签**（该值在补齐 `SourceBounds` 之前只能覆盖词条匹配一处），
   Seamless 的前提成立；
2. 快速首显的 `IsTrusted` 准入在这些画面上不会筛掉任何标签，首显即完整输出。

**关于 100% 高置信度的核实结论**（已用 `匹配来源=` 这一行查清，非猜测）：

| 实测图 | 命中 | 匹配来源 |
|---|---|---|
| QQ20261007-173014 | 9 | 精确 9 / 模糊 0 / 布局 0 |
| QQ20261007-124246 | 4 | 精确 3 / 模糊 0 / 布局 1 |
| QQ20261007-144653 | 2 | 全部为词条精确匹配 |

原因是这些画面里的词条命中**恰好都是精确匹配**（得 70 分 → 高置信度），
再加上固定锚点布局标签也标为高置信度，因此没有中/低置信度出现。

**结论：置信度判定并未偏宽松**，`IsTrusted` 过滤与「低置信度二次 OCR」在这类画面上
只是没有触发条件。要覆盖模糊匹配（OCR 噪声经近似修复）那条路径，需要实机画面中
出现带噪声的识别文本才能观察到——这属于实机验证范围。

**仍待实机确认**：OCR 噪声场景下模糊匹配是否会被正确判为中等置信度，
从而让复核路径真正工作。

## 二、Seamless 阈值诊断（重要：实机调优依据）

双渲染用「背景离散度 ≤ 26」决定是否把原文区改成无缝原位替换，否则回退卡片。
本项诊断回答：这个阈值在真实画面上会不会让 Seamless 实际生效。

统计量与 `OverlayFrame.SampleSeamlessBackgrounds` 完全一致：
在区域上按 stride（宽/24、高/12）采样，求 RGB 三通道标准差的平均值。

### 发现 1：测量尺度显著影响结论

同一张 `QQ20261007-173014.png`，只改变测量格子大小：

| 格子尺寸 | 中位离散度 | ≤26 占比 |
|---|---|---|
| 90×18 | 40.3 | 21.1% |
| 60×16 | 35.6 | 26.0% |
| 40×14 | 32.0 | 34.1% |
| 24×12（接近真实 OCR 文字框） | 28.9 | 41.1% |

格子越小越接近应用实际采样的 OCR 文本框，离散度越低。
因此**用大网格扫全屏会系统性高估离散度，不能直接据此判断阈值是否合适。**

### 发现 2：全屏分布（4 张实测图，90×18 网格，各 1428 区域）

| 图片 | 中位离散度 | ≤26 占比 |
|---|---|---|
| QQ20261007-123533 | 31.17 | 40.3% |
| QQ20261007-124246 | 33.29 | 37.3% |
| QQ20261007-124306 | 33.76 | 36.7% |
| QQ20261007-124323 | 33.55 | 38.0% |

分位：P10=15.1、P25=21.0、P50=33.1、P75=52.7、P90=69.7。

不同阈值下「可无缝替换」的全屏区域占比：10→4.4%、15→9.7%、20→22.5%、
**26（当前）→38.1%**、35→52.8%、50→72.3%。

### 结论与限制

1. 全屏统计包含大量**非文字区域**（地面、树木、砖墙纹理），而应用只采样
   **被 OCR 识别且命中词条的文字框**，那些多位于 UI 面板内、背景更均匀。
   故上表占比是**下界**，真实触发率应更高，但无法由静态图推断确切值。
2. 阈值 26 偏保守，这是有意方向：施工单要求背景复杂/动态/半透明时回退卡片，
   宁可不够漂亮也不能污染画面。
3. **是否放宽必须由实机观感决定**。实机验证时应记录：
   - 高置信度标签中实际走 Seamless 的比例；
   - 是否存在「色块比卡片更显眼」（阈值过松）；
   - 是否存在明显可无缝却回退卡片（阈值过严）。
4. 半透明覆盖层、动态特效等「可估计但不应无缝」的情形，当前仅凭离散度无法识别，
   属已知局限，留待实机观察后决定是否增加判据。

## 四、测试链路前置修复（环境相关）

本机仓库位于含中文目录的路径下，带来两个与代码无关的环境障碍，已修复：

1. `Assembly.LoadFile` 会把该路径下的程序集判为「远程源」而拒绝加载。
   新增 `tests\Load-TestAssembly.ps1`：先试 `LoadFile`，仅在遇到该错误时改用
   `UnsafeLoadFrom`（官方「调用方保证本地」的 API）。同一程序集、同样断言，未放宽任何测试。
2. 用 `Start-Process` 启动 EXE 会触发 Windows 附件管理器的「发布者未知」确认框
   （该路径被判为 Internet 区域）。新增 `tests\Start-ProductExe.ps1`，
   改经 `CreateProcess` 直启（`UseShellExecute = false`），不触发该对话框，
   且未修改任何系统安全设置。

## 五、桌面「未知发布者」弹窗的根因与修复

排查中发现一个会打断玩家的真实缺陷，值得单独记录。

**现象**：运行测试套件时桌面反复弹出 `Open File - Security Warning`，
标题为 `...\.bench\application-updater-test\安装目录\枫语幕.exe`。

**根因**：不是测试脚本直接启动，而是**产品代码**里的收尾步骤。
`src\ApplicationUpdater.cs` 的 `StartInstalledApplication()` 与 `StartInstaller()`
用 `Process.Start(..., UseShellExecute = true)` 启动「更新后安装目录里的 `枫语幕.exe`」。
`tests\logic-application-updater.ps1` 会建一个沙箱目录、放入**同名文本占位文件**，
再驱动真实的更新流程；替换成功后产品按设计去启动新版本，于是 ShellExecute 了那个
占位文件，Windows 因未签名而拦截并弹框。

**证据**：Windows 事件日志中 `Wow64 Emulation Layer` 条目与跑测试的时刻逐一对齐
（16:49:34、16:53:00、17:00:31、17:03:26、17:25:57 等），路径正是该沙箱。

**修复**：

- `src\ApplicationUpdater.cs` 新增 `AutomationPolicy.SkipGuiRestart`
  （读环境变量 `FENGYUMU_AUTOMATION=1`），两条启动路径在该标志下直接返回；
  更新本身的校验、备份、替换、回滚逻辑不受影响，真实升级时行为完全不变。
- 新增 `tools\Invoke-AutomatedRegression.ps1`：统一的测试入口，运行前自动设置该标志。
  **以后跑回归应一律走这个入口**，不要手工逐个调脚本。
- 新增 `tools\Measure-TranslationPerformance.ps1`：性能基准入口，同样带该标志，
  并经 `Start-ProductExe`（CreateProcess）启动产品。

**验证**：修复后重跑更新测试，退出码 0、功能断言全部通过，
且事件日志中**不再出现**任何尝试启动沙箱占位文件的记录。

**附带修复**：翻译时若遇到全屏或未找到窗口，原先会弹模态框抢走游戏焦点；
现改为屏幕中央提示 3.5 秒自动消失（`NotifyLockProblem` / `PaintLockNotice`），
玩家不需要点击任何东西。其余 `MessageBox` 仅在用户主动打开设置或检查更新时出现。

## 六、Seamless 触发率的离线实测（重要结论）

`last_run.txt` 现有 `源区域=` 一行，记录每个标签**实际用于擦除的矩形**
（即渲染器真正会采样的区域）。把它与基准图片对照，就能在**不接触运行中游戏**的前提下
复现渲染决策。

复现脚本按与 `TrySampleUniformBackground` 完全相同的算法（stride 宽/24、高/12，
三通道标准差取平均）测量每一块源区域：

| 实测图 | 标签 | 判定无缝 | 精确源区域离散度 |
|---|---|---|---|
| QQ20261007-173014 | 9 | 0 | 33.8 / 42.0 / 42.9 / 49.5 / 51.4 / 52.5 / 59.4 / 64.0 / 81.2 |
| QQ20261007-144653 | 2 | 0 | 38.3 / 48.6 |
| QQ20261007-124246 | 4 | 0 | 33.2 / 35.9 / 54.7 / 57.6 |
| QQ20261007-123533 | 1 | 0 | 54.4 |

**结论：修复前 16/16 个标签全部远超阈值 26，Seamless 触发率为 0%。**

### 已实施的修复：分离墨迹与背景

原判据有一个可证明的缺陷：采样区域**包含文字笔画本身**，笔画与底板混合会把离散度
推得很高。实测黑字在纯色底板上会得到约 **90** 的离散度，被误判为「纹理」，
于是 Seamless 在所有截图上都不可达。

现改为：

1. 先求区域内像素的**中位数颜色**，作为背景色估计；
2. 只保留接近该中位数的像素（即**背景**），排除文字笔画；
3. 对背景像素求离散度，并要求**覆盖率 ≥ 0.35**（背景必须占主导）；
4. 像素经 `LockBits` 一次性读入，不再逐像素 `GetPixel`。

修复后（用同步了该算法的离线脚本复现）：

| 实测图 | 可采样标签 | 判定无缝 | 离散度 |
|---|---|---|---|
| QQ20261007-124246 | 1 | **1** | **4.3** |
| QQ20261007-173014 | 1 | 0 | 4.3 |

即：算法现在能**正确识别出纯色底板**（离散度 4.3，远低于阈值），同时仍拒绝纹理区域——
`logic-overlay-dual-rendering.ps1` 确认渐变背景依旧被拒，说明中位数滤波没有让渐变蒙混过关。

多数标签仍因**覆盖率不足**被拒，这与「MapleStory 文字多绘制在游戏世界纹理上」的
观察一致：它们本就应当回退卡片。

### 采样耗时实测

`LockBits` 改造后，反射调用**真实实现**测得：

| 区域 | 面积 | 单次耗时 |
|---|---|---|
| 60×16 | 960 px | 0.457 ms |
| 120×24 | 2880 px | 0.260 ms |
| 300×40 | 12000 px | 0.328 ms |

约 **0.3–0.5 ms/标签**；9 个标签合计约 3–5 ms，可忽略。
改造前逐像素 `GetPixel` 约为 73 ms/标签，相差约两个数量级。

**根本原因**（已用截图与坐标双重确认）：MapleStory 的界面文本**直接绘制在游戏世界
纹理之上，没有纯色底板**——草地、树屋、泥地。经核对 `任务助手` 标签位于 X≈1578，
该处背景是绿色草坪而非灰白面板，坐标与画面吻合，说明测量无误。

**这是正确行为，不是缺陷**：在纹理背景上强行无缝替换会留下明显色块，比卡片更差。
`CardFallback` 正是施工单要求的「宁可不够漂亮也不能污染画面」的选择。

**但它同时说明**：双渲染的 `Seamless` 分支在当前游戏画面中**基本不会启用**，
只有背板本身是纯色的元素（如聊天框、不透明菜单）才可能命中。

**可选的后续调优方向**（留待实机观感后决定，本轮不擅自改）：
当前判据只看「整块区域的离散度」，而文字本身的笔画会抬高该值。若改为
**只采样文字行的上/下边缘带、或采用中位数与边缘一致性判据**，能更准确地区分
「纯色底板上的文字」与「纹理上的文字」。本轮不改，因为改判据需要真实观感验证。

- 「首次可见」＝截图 + 快速探测 + 主 OCR 与匹配，即主通道完成后高置信度子集可立即上屏的时刻。
- 「最终收敛」＝标签集合停止变化的时刻，等于 `耗时毫秒`。
- 改动前基线：任务面板 1246 ms（截图 40 ms / 主 OCR 与匹配 626 ms / 面板复核 462 ms）。
  整治后收敛 1288 ms，未超出基线 +10%（≈1371 ms）。
- 待命状态不运行 OCR、不调用联网 AI，仅 1 秒一次的窗口几何轮询。

### 待命开销实测（施工单要求「待命 CPU 增量接近零」）

初次实测发现锁定层单次轮询 **56.71 ms**，待命占空比 **5.67%**，明显不达标。
根因是窗口枚举对每个顶层窗口都调用 `Process.GetProcessById` 解析进程名，
而该调用会构造完整的进程对象。

改用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` +
`QueryFullProcessImageName` 读取映像名（单次只读调用，不申请任何 `PROCESS_VM_*` 权限）后：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 单次轮询（平均 / 中位 / 最大） | 56.71 / 56.32 / 69.01 ms | **0.72 / 0.60 / 1.63 ms** |
| 待命占空比（1 秒轮询） | 5.67% | **0.072%** |

安全边界随之收紧：锁定层只使用只读查询权限，测试断言据此改为
**禁用 `PROCESS_VM_READ`/`PROCESS_VM_WRITE`/`PROCESS_VM_OPERATION`/`PROCESS_ALL_ACCESS`/
`PROCESS_CREATE_THREAD`**，而不是笼统禁止 `OpenProcess`——危险的是申请的权限，
不是这个调用本身。
